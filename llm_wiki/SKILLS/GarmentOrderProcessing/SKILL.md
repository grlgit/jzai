# 服装订单处理技能 (GarmentOrderProcessing)

本技能实现从订单原始文件到ERP系统录入的完整流程。整个过程分三个阶段：解析订单、查询知识库、生成ERP订单。

## 整体流程

```
订单文件 (Excel/PDF)
        │
        ▼
  ┌─────────────┐
  │ 阶段1: 解析  │  提取基本信息
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │ 阶段2: 查询  │  从Wiki获取生产要求
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │ 阶段3: 生成  │  组装参数 → 调用ERP接口
  └─────────────┘
```

---

## 阶段1: 理解订单内容

从用户对话上下文中获取订单文件并解析其内容。订单文件没有固定格式，信息项目因客户和订单类型而异，需要自行理解文件内容，识别出所有有价值的信息。

### 核心目标

从订单中理解两类信息：

1. **订单事实** — 文件中直接包含的所有信息，如款号、数量、交期、客户名称、面料、价格等。不要预设哪些字段"必须"存在，而是尽可能完整地提取文件中实际包含的所有信息。

2. **查询线索** — 从订单内容中识别出可用于从Wiki知识库匹配生产标准的关键维度，通常包括但不限于：客户、品牌、款式类别、面料类型等。这些线索将在阶段2中用于构建查询。

### 理解要点

- 不同订单的信息结构差异很大，有的有PO号，有的没有；有的标注了面料成分，有的只有款号和数量。按文件实际内容提取，不要硬套固定模板。
- 分色分码数量表是服装订单的核心数据，通常以矩阵形式呈现（行=颜色，列=尺码），需要完整提取。
- 如果订单信息明显不完整（如缺少客户或款号），向用户确认后再继续。

## 阶段2: 从Wiki知识库获取生产信息

根据阶段1理解到的订单内容，通过MCP工具查询Wiki知识库中的生产要求。

### 查询策略

先调用 `mcp__llmwiki__guide` 了解知识库结构，然后根据订单信息智能构建查询。

关键原则：**不同的生产环节与不同的查询维度相关，不要机械地用所有维度去查所有环节。** 需要根据服装行业知识判断每个环节与哪些维度最相关。

例如：
- **标签挂卡** 通常由客户和品牌决定，与款式类别无关 — 查询时用客户+品牌，忽略款式类别
- **车缝要求** 既与款式类别相关（外套和衬衫的车缝完全不同），也可能有客户特殊要求 — 需要分别查询款式类别的通用标准和客户的特殊要求
- **包装要求** 可能与客户、品牌、产品线都有关联
- **面料检验标准** 可能与面料类型相关，而非客户或款式

查询时应灵活组合维度，如果某个查询没有结果，尝试放宽条件重新查询。

### 需要获取的生产信息

主要包括但不限于：车缝要求、包装要求、标签挂卡要求、船样要求、质量标准、面辅料要求等。具体需要查询哪些环节，取决于订单内容和知识库中实际存在的信息。

如果某些信息在Wiki中查询不到，在最终输出中标注为"待补充"并提醒用户。

---

## 阶段3: 生成ERP订单

将阶段1和阶段2收集到的信息，按ERP订单模板格式组装，然后调用ERP接口。

### ERP订单参数模板

读取 `references/erp_order_template.json` 获取ERP订单的数据格式模板。模板定义了三个部分：

- **order_header** — 订单头信息（款号、客户、交期、提货港等）
- **order_lines** — 订单明细行，每个条目对应一个颜色+尺码的组合，由分色分码表展开生成
- **production_specs** — 从Wiki获取的生产要求（车缝、包装、标签、船样、质量、面辅料）

按模板结构填充数据后组装为请求体。如需自定义模板，修改 `references/erp_order_template.json`。

### ERP接口配置

接口参数在技能配置文件 `erp_config.json` 中定义（参见下方配置文件说明）。调用时：

1. 读取 `erp_config.json` 获取接口地址和认证信息
2. 按模板格式组装请求体
3. 通过HTTP POST发送到ERP接口
4. 检查返回状态，向用户报告结果

```bash
curl -X POST "${erp_base_url}${erp_endpoint}" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer ${erp_token}" \
  -d '${order_payload}'
```

### 生成前确认

在实际调用ERP接口之前，必须将组装好的订单数据展示给用户确认：

1. 显示订单基本信息摘要
2. 显示分色分码数量汇总表
3. 显示从Wiki获取的生产要求要点
4. 列出缺失或待补充的信息
5. 等待用户确认后再提交

这一步非常重要 — 订单一旦录入ERP通常需要走审批流程才能修改，所以在提交前给用户充分的审核机会。

## 配置文件: erp_config.json

在技能目录下创建 `erp_config.json` 来配置ERP接口连接信息：

```json
{
  "erp_base_url": "https://erp.example.com/api",
  "erp_endpoint": "/orders/create",
  "auth_type": "bearer",
  "auth_token": "YOUR_TOKEN_HERE",
  "timeout_seconds": 30,
  "order_template": "default",
  "custom_field_mapping": {},
  "retry_on_failure": true,
  "max_retries": 3,
  "dry_run": true
}
```

| 配置项 | 说明 |
|--------|------|
| `erp_base_url` | ERP系统API基地址 |
| `erp_endpoint` | 创建订单的接口路径 |
| `auth_type` | 认证方式：`bearer`, `basic`, `api_key` |
| `auth_token` | 认证凭据（Bearer token / API key） |
| `timeout_seconds` | 请求超时时间 |
| `order_template` | 订单模板名称，`default` 使用内置模板 |
| `custom_field_mapping` | 自定义字段映射，用于将内部字段名映射到ERP系统字段名 |
| `dry_run` | 设为 `true` 时只组装数据不实际提交，用于测试 |

### 自定义字段映射示例

当ERP系统的字段名与默认模板不同时，通过 `custom_field_mapping` 映射：

```json
{
  "custom_field_mapping": {
    "style_no": "item_code",
    "customer": "buyer_name",
    "delivery_date": "ship_date",
    "color": "colour",
    "qty": "quantity"
  }
}
```

## 错误处理

- **文件读取失败**：提示用户检查文件路径和格式是否正确
- **关键字段缺失**：列出缺失字段，请用户手动补充
- **Wiki查询无结果**：标注"该信息在知识库中未找到，请确认是否已录入"，继续处理其他信息
- **ERP接口异常**：显示错误码和消息，建议用户检查 `erp_config.json` 配置或联系IT
